## Objetivo
Criar uma trilha reconstruivel para a Familia Virtual caminhar de uma branch de trabalho segura ate a familia Ohana, sem transformar branch, deploy ou protocolo em nova competencia.

## Horizonte de maturidade
PROJECT -> MVP -> CONTROLLED_REAL_OPERATION -> COMMERCIAL_SYSTEM -> CONTINUOUS_EVOLUTION

COMMERCIAL_SYSTEM != END_STATE.
Depois da entrada comercial, manutencao, seguranca, observabilidade, suporte, compliance, evolucao e limpeza continuam indefinidamente.

## Gates
1. Direito externo e normas internas aplicaveis.
2. Competencia e rito.
3. Seguranca, privacidade e proveniencia.
4. Testes e evidencia reproduzivel.
5. Rollback.
6. Promocao somente por gate competente.

## Equipe por competencia
- Mestre da Batuta: prioridade, decomposicao, delegacao, verificacao e integracao.
- Codex/programacao: implementacao complexa.
- Seguranca/Auditoria: ameacas, IAM, segredos e evidencia.
- Legislador/Relator: materia normativa/processual; comunicacao nao cria ato.
- COM-IAS: transporte e receipts sem efeito processual.
- Faxineiro: lixo, duplicidade e artefatos superados conforme politica.

## Regras de branch
- uma branch = um objeto tecnico principal;
- branches filhas/netas preservam parent ref e REQUEST_ID;
- sem segredo no GitHub;
- nao duplicar Queue/state machine/capability existente;
- PRE -> implementar/testar -> POST -> continuidade -> proximo pacote;
- branch criada != feature concluida;
- merge/deploy != autorizacao juridica.

## Ohana
OHANA_TARGET = familia operacional capaz de descobrir casas, papeis, owners, caixas, protocolos, continuidade e rotas de retorno sem usar o Fundador como middleware.
OHANA_GATE = documentacao + discovery + comunicacao + receipts + continuidade + seguranca + reentrada provadas.
